[11] 异构数据预处理与垂直领域知识库的搭建

[12] 本阶段需对考研核心权威资料（如《数据结构》等官方指定教材及历年统考真题）进行精细化处理并入库。针对大量扫描版 PDF 教材存在的文字层乱码（水印广告）等技术阻碍，需设计并部署一套基于高精度云端 OCR 的自动化文本提取与去噪清洗流水线。此外，为避免常规的固定字数分块（Fixed-size Chunking）方法将连贯的 C 语言逻辑代码或复杂的数学公式强行物理截断，必须探索并实现更为智能的“语义分块（Semantic Chunking）”策略。最后，调用预训练模型将处理后的原子文本块转化为高维 Embedding 向量，并持久化存储至 ChromaDB 向量数据库中，为整个智能问答系统夯实底层的知识底座。

[13] 后端核心服务架构的开发与 RAG 业务链路贯通

[14] 采用 FastAPI 等现代化的异步 Web 框架，独立完成系统后端底层服务的开发。本阶段需将“用户提问 → 高维向量检索（Top-K 召回） → 组装约束性 Prompt → 大模型生成回答”这一最核心的 RAG 业务闭环完全打通。同时，为满足任务书中“单轮首字响应延迟必须严格控制在 3 秒以内”的硬性交互指标，必须彻底摒弃传统的等待全文生成后返回的阻塞模式，全面接入 SSE（Server-Sent Events）实时流式推流技术，实现大模型推理结果的逐字平滑输出。此外，还需同步完成多轮对话上下文的历史状态管理、用户会话列表维护，以及核心的知识溯源定位等辅助性 RESTful API 接口的开发与调试。

[15] 前端交互界面的搭建与多模态复杂内容的富文本渲染

[16] 在用户交互可视化层面，采用 Vue 3 渐进式框架搭配 Element Plus 基础组件库，构建响应式的 Web 端智能学习平台。前端工程不仅要深度对接后端的 SSE 流式输出接口，最关键的攻坚任务是解决考研计算机领域复杂多模态内容的无损展示问题——系统必须能够原生支持复杂 Markdown 文档的结构化解析、C 语言等代码块的动态语法高亮，并集成 KaTeX 等高性能排版引擎将复杂的数学推导公式（如时间复杂度分析）进行出版级渲染。此外，前端界面必须强制规划并实现“知识来源引用（Citation）”的可视化侧边栏功能，让学生能在对话中精准追踪并确认答案出自哪一本权威教材的哪一具体物理页码，确立系统的学术公信力。

[20] 二、目前已完成任务情况

[21] 复杂异构数据的深度预处理与自动化 OCR 流水线基建

[22] 构建垂直领域 RAG（检索增强生成）系统的首要环节，是获取纯净、结构化且具备精准定位信息的高质量语料库。本课题选取了《数据结构考研复习全书》（竟成 2027 版）作为核心语料。在数据解析初期，系统遭遇了严峻的底层技术挑战：由于市面上流通的教材多为扫描版 PDF，其本质为图像集合而非文字对象，导致常规 PDF 解析库（如 PyMuPDF、pdfplumber）无法直接提取内容。

[23] 针对上述“扫描版 PDF 文本提取障碍”，本课题先后探索并对比了三种技术路径：

[24] 检索原生数字版文档（Native PDF）。曾尝试在各大开源社区及学术数据库中寻找高质量的文字版或 LaTeX 源码文档。经评估，虽然原生数字版文档提取难度最低，但 408 考研领域的权威教材资源受版权保护，互联网公开资源极其稀缺，且非官方版本存在内容滞后、公式错漏等质量问题，无法满足考研备考的严谨性要求，故放弃。

[25] 基于大模型 API 的结构化解析与智能修复（LLM-based Doc Repair）。尝试利用高性能大模型（如 Kimi）的文档解析能力，通过 API 调用将原始字节流或乱码文字层输入模型进行语义重构与格式修复。实验发现，虽然该方案在处理复杂排版和代码识别上表现出极高的智能化潜力，但面对近 500 页的厚重教材，其产生的 “Token” 消耗量呈指数级增长，单次全书处理的经济成本远超本科毕业设计的预算范畴。这种高昂的推理成本不符合系统“低成本、高效率”的设计初衷，在工程经济性评估中被否决。

[29] 基于异步协程的高并发图像光栅化与云端识别

[30] 流水线首先利用 PyMuPDF 引擎将 491 页 PDF 文档执行高分辨率光栅化（Rasterization）渲染，转化为 PNG 图像序列。为突破单线程网络 I/O 的阻塞瓶颈，系统基于 Python asyncio 异步框架构建了高并发协程池，实现了对百度云 OCR（accurate_basic 高精度版）接口的批量并行调用。该异步调度机制显著提升了处理效率，确保了整本厚重教材能在数分钟内完成零失败的自动化解析。

[31] 噪声抑制与正则清洗矩阵（RegEx Cleaning Matrix）

[32] 针对识别结果中密布的防盗水印（如“内部资料，侵权必究”）及商业推广文字，系统开发了多维度正则表达式（RegEx）过滤算子。在不损伤正文逻辑的前提下，剔除各类干扰字符串。同时，针对目录解析中常见的空格缺失问题，引入正则后向查找补位机制，自动化优化文本排版，为后续语义切片提供标准化语料。

[33] 自适应页码偏移校准算法（Page Offset Calibration Algorithm）

[39] 文本分块（Chunking）机制不仅决定了知识切片的粒度冗余度，更直接决定了 RAG 架构在检索阶段的语义召回精度（Recall）。传统方案广泛采用的“固定长度滑动窗口切分（Fixed-size Chunking）”存在严重的机械性弊端：其忽视了自然语言的逻辑边界，极易将连续的 C 语言逻辑代码从中间截断，或将算法的前提条件与时间复杂度推导结论强行分离。这种“语义碎片化”现象会严重破坏知识域的连贯性，导致大模型在生成阶段因上下文缺失而产生逻辑错误 。

[40] 为了彻底提升系统对专业知识的主题一致性，本系统研发并部署了前沿的“上下文感知语义分块策略”。该算法通过双层架构设计，实现了从物理边界到语义深层的精准切分 ：

[41] 物理与逻辑层级的确定性硬切分

[49] 多维意图解析与语义知识召回

[50] 当系统路由接收到用户提问时，首先通过内存驻留的 BGE-m3 多语言嵌入模型，将查询文本转化为 1024 维的高维度稠密向量（Dense Vector）。随后，在 ChromaDB 向量数据库内部执行近似最近邻（ANN）相似度计算，提取出最具相关性的教材原文片段（Top-K Chunks）。该过程利用向量语义对齐技术，确保了即便用户提问与教材原话在措辞上不完全一致，系统仍能准确命中核心考点。

[51] 严苛约束的提示词工程（Prompt Engineering）

[52] 提取后的文档内容将作为“外部真理（Ground Truth）”注入系统内置的提示词模板中。本系统设计了复杂的指令驱动型提示词（Instruction-based Prompt）：通过“仅限基于参考资料回答”、“严禁引入外部无关知识”以及“若无相关信息请回答不清楚”等强约束指令，从输入端强制收敛 LLM 的生成空间。这一机制是系统实现“零捏造、零幻觉”目标的核心技术手段。

[53] SSE 异步流式推流（Server-Sent Events）

[54] 为克服 LLM 推理延迟，后端接入兼容 Anthropic API 规范的高性能接口。利用 Python 的 AsyncIterator 异步迭代器实时捕获云端吐出的每一个 Token 流。同时，在 FastAPI 中封装 StreamingResponse 对象，将响应内容类型（MIME Type）严格设置为 text/event-stream。这种“打字机式”的下行传输机制彻底突破了响应时延壁垒，将感知延迟（TTFT）控制在毫秒级，确保了用户端的实时交互流畅度。

[55] 有状态会话的持久化与上下文记忆管理

[56] 为支持 408 考点中常见的带有强代词指代（如“该算法”、“其复杂度”）的多轮追问，后端搭建了基于服务器内存对象的历史会话池（Session Memory Pool）体系。系统在每次触发生成前，会自动提取最近 N 轮的交互消息字典作为对话语境（Context Window），通过动态补全语境信息，显著提升了模型在复杂推导场景下的语义焦点稳定性与逻辑一致性。

[92] 三、存在的问题和拟解决方法

[93] 扩展知识库覆盖范围

[94] 存在问题：当前系统的垂直知识底座仍处于单点突破阶段，仅完成了《数据结构》单科教材的自动化提取与向量入库，尚未覆盖 408 统考大纲中《操作系统》、《计算机网络》及《计算机组成原理》三门核心科目。同时，现有语料库极其缺乏历年真实考题及权威解析数据作为“基准真理（Ground Truth）”支撑。这种单学科的“数据孤岛（Data Silo）”局限性，导致系统目前无法应对考研真题中极具难度的跨学科横向综合性提问（例如页表结构往往涉及计组与操作系统的交叉考查），距离满足考研学子全维度、跨学科复习的实际业务需求仍存在显著差距。

[95] 拟解决路线：针对上述语料广度瓶颈，项目组计划于第 11 周全面启动数据扩容与横向融合工程。首先，多渠道系统性地收集其余三科的权威教材（含扫描版及高清数字版）以及近十年 408 统考全科目真题集。在底层基建与工程实施层面，将全面复用并横向扩展前期已跑通且通过压测的标准化高效处理流水线——即“高并发云端 OCR 提取 → 正则清洗矩阵去噪 → 自适应页码偏移校准 → 语义感知分块（Semantic Chunking）”。系统将依托异步并发调度机制，完成大规模、全科目异构语料的批量化入库作业。更关键的是，入库过程中将深度提取并映射全书的目录树元数据（Metadata），通过多维度的标签体系在不同学科的底层概念之间建立强关联索引，最终构建出一个真正覆盖 408 全考点、逻辑严密且支持多学科融合的终极垂直考研知识库。

[96] 完善检索与生成策略

[97] 存在问题：目前后端架构在 RAG 链路上仅实装了基于 ChromaDB 的单一稠密向量检索机制（Dense Retrieval）。高维稠密向量在捕捉宏观句式意图和语义泛化方面表现卓越，但 408 考研学科语料中充斥着海量的专业英文缩写（如“CSMA/CD 协议”、“TLB 快表”）、底层硬件寄存器编号（如“R0 寄存器”）以及特定算法常数。这类低频、高信息熵的实体词汇极易在高维向量空间中发生“特征坍缩（Feature Collapse）”。因此，单纯依赖语义相似度的检索引擎在面对要求字面精确匹配（Exact Lexical Matching）的硬核长尾提问时，存在明显的召回天花板与严重的知识遗漏隐患。

[98] 拟解决路线：为彻底打破单一检索机制的召回率瓶颈，系统计划于第 12 至 13 周实施检索引擎的核心架构迭代。

[99] 实装倒排索引与混合检索（Hybrid Retrieval）

[100] 旁路引入轻量级倒排索引引擎（如 ElasticSearch 或 Rank_BM25），实装基于词频-逆文档频率的 BM25 稀疏关键字检索策略。该算法对罕见专有名词与数字编号具有极端的词法敏感度，可有效保障绝对字面匹配的底线召回率，从而与稠密向量形成“语义+词法”的优势互补。

[101] 基于 RRF 的异构量纲融合

[102] 为科学解决稠密语义分数与稀疏词法分数因物理量纲不同而导致的融合排位难题，系统将引入倒数排序融合算法（Reciprocal Rank Fusion, RRF）。通过无监督公式，对两路独立召回的候选集合进行交叉重打分与序列融合。

[103] 交叉编码器（Cross-Encoder）极致精排

[104] 为彻底拦截因多路扩充召回带来的底层词法噪音，在将最终上下文递交给大模型前，检索链路末端将挂载智源 BGE-Reranker-base 等交叉编码器执行重排（Reranking）。交叉编码器将对“提问-文档（Query-Document）”对进行深度的全注意力机制（Full-Attention）交互打分，执行极致精筛。

[105] 系统测试与效果评估

[106] 存在问题：现阶段针对大模型生成质量的检验，开发组仍停留在依赖人工输入离散测试用例（如“请解释快速排序”）并进行主观肉眼比对的“启发式抽检（Heuristic Inspection）”阶段。系统内部严重缺乏标准化、可复现的自动化定量评估基准（Benchmark）。这种定性主观的测试模式，导致任务书中承诺的“单轮首字响应延迟 ≤ 3秒”以及“系统生成准确率 ≥ 80%”等严苛工程指标，目前仅停留在理论声明层面，极其缺乏大规模压测下的量化数据与置信区间支撑。

[107] 拟解决路线：在第 13 至 14 周的系统验收期，项目组将全面摒弃主观测试，转向数据驱动的工程量化测试范式，具体实施路径分为三个层级：

[108] 构建 408 专属评测基准（Golden Standard Benchmark）：脱离开发环境，精心构造一套涵盖概念辨析、复杂算法计算、底层架构综合案例等高频考点的高质量测试集，并为每道题目赋予经专家人工标定的基准真理答案（Ground Truth），作为模型表现的对标锚点。

[109] 实装 RAGAS 自动化评估矩阵（LLM-as-a-Judge）：突破传统基于字符串重合度（如 BLEU/ROUGE 算法）在长文本评估上的局限性，系统将引入当前学术界最具权威性的 RAGAS（Retrieval Augmented Generation Assessment） 自动化评估框架。利用大语言模型极强的语义理解能力充当“裁判”，重点轮测并量化三大黄金维度的分数矩阵：

[110] 忠实度（Faithfulness）：严苛判定生成内容是否完全从检索到的上下文中推导而出，量化系统的“抗幻觉”能力；

[111] 答案相关性（Answer Relevancy）：运用余弦惩罚机制检验回复是否切中要害、拒绝冗余跑题；

[112] 上下文精度与召回率（Context Precision & Recall）：从源头剖析底层检索引擎是否成功召回了回答该问题所必需的全部核心切片。

[113] 高并发负载测试与性能边界探勘：为印证系统底层架构的健壮性，将实装 Apache JMeter 等工业级压测工具。通过配置多线程虚拟用户群模拟高峰期访问流，对系统的 SSE 异步推流接口执行极限压测。重点监控并记录不同并发梯度下的首字响应延迟（TTFT, Time to First Token）、QPS（每秒查询率）极值以及内存垃圾回收（GC）状态。

[114] 3.4 工程封版验收与学位论文撰写

[115] 存在问题：随着前端“知识库阅读器”与后端 SSE 流式推流等核心模块的提前上线，本课题的软硬件工程开发已基本接近尾声。当前面临的主要挑战是：前期长达数周的敏捷开发沉淀了海量的非结构化技术文档、复杂的微服务架构逻辑，以及即将在测试期产出的庞大量化性能数据。如何将这些高密度的工程实践成果与算法原理，严格按照学术规范转化为逻辑严密、论证充分的本科毕业设计论文，并顺利通过查重与格式审查，是现阶段的最后一道难关。

[116] 拟解决路线：在第 14 至 15 周的最后冲刺阶段，项目组将全面停止新增边缘业务代码，进入严格的系统功能封版（Feature Freeze）阶段，将全部精力向学术写作与答辩筹备倾斜：

[117] 架构梳理与核心算法可视化：系统性地回溯并精修全套系统工程图例（涵盖 UML 类图、系统部署图、异步交互时序图等）。针对课题的核心技术壁垒（如“自适应页码偏移校准算法”、“向量空间驱动的语义分块”、“RRF 混合检索重排”），提取并凝练出标准化的学术伪代码（Pseudocode），全方位提升论文的技术深度。

[118] 测试数据图表化与正文撰写：深度整合前期基于 RAGAS 评估框架与 JMeter 压测产出的量化分数矩阵，将其转化为具有强学术说服力的雷达图、折线图及对比表格。在此数据支撑下，严格遵照燕山大学教务处关于字数、排版规范及查重率的要求，高质量完成论文正文的撰写及规定字数的外文文献翻译工作。
